# run-log

## このスキルがすること

ランニング記録のインプット（スクリーンショット画像 or 文字起こしテキスト）を受け取り、以下を一気通貫で行う。

1. データ抽出（サマリー + スプリット）
2. 対象の大会ディレクトリの特定
3. `results.csv` / `splits.csv` への追記
4. `plan.md` との照合
5. `evaluations.md` への評価コメント追記
6. 変更のコミットと `main` へのpush

各ファイルのカラム定義・データ規約はリポジトリ直下の `CLAUDE.md` に定義されている。矛盾があれば `CLAUDE.md` を正とする。

## Step 1: データを抽出する

画像が渡された場合は Read ツールでそのまま読み込んで内容を読み取る。テキストが渡された場合はそのテキストから同様の項目を読み取る。

読み取る値は2種類ある。

**サマリー（1走行につき1組）**

`date, start_time, end_time, distance_km, avg_pace_sec, best_pace_sec, running_time_sec, elapsed_time_sec, calories_kcal, avg_cadence_spm, elevation_gain_m, elevation_loss_m, avg_hr_bpm, max_hr_bpm`

**スプリット（km単位、画面にあれば取得。無ければスキップしてよい）**

`date, start_time, km, split_pace_sec, pace_diff_sec, elevation_change_m, hr_bpm`

抽出時の変換ルール:

- ペース・時間はすべて秒数の整数に変換する。表示形式の文字列（`6'23"` や `50:09`）はCSVに残さない。`分'秒"` 形式も `MM:SS` 形式も「分×60＋秒」で秒数化する
- 高低差は上りを正、下りを負の数（メートル）で記録する。サマリーは `+53m` → `elevation_gain_m=53`、`-55m` → `elevation_loss_m=-55`。スプリットの `elevation_change_m` も表示どおり符号付きで記録する（`-23m` → `-23`）
- スプリットの `start_time` はサマリーの `start_time` と同じ値を入れる（`date` と `start_time` の組で `results.csv` と紐付ける）
- スプリットの `km` は区間の終点までの累計距離。1km区間は `1, 2, …`、最後の端数区間は走行距離そのものにする（画面上で `0.12km` と表示される8km目の次の区間は `8.12`）。最後の行の `km` がサマリーの `distance_km` と一致することを確認する
- スプリットの `pace_diff_sec` は前kmとの差分。表示が `+0'14"` なら `+14`、`-0'06"` なら `-6` のように符号付き秒数にする
- 読み取れない・画面に存在しない項目は空欄のままにする。値を推測して埋めない

スプリットに歩きを含むとみられる区間（他のkmより大幅に遅い、経過時間とランニング時間の差が大きいなど）がある場合は、Step 5で評価を書く前に、その回の目的・状況（ファンラン、レース、途中で歩いた、信号待ちなど）をユーザーに確認する。CSVへの追記は確認の前に行ってよい。

## Step 2: 対象の大会ディレクトリを特定する

`races/` 配下は `races/YYYY-MM-DD-大会名/` という命名になっている。以下の手順で書き込み先を決める。

1. `races/` 配下のディレクトリを列挙する
2. ディレクトリが1つもなければ、大会ディレクトリの作成はこのスキルの範囲外なので処理を止め、大会ディレクトリをまず作る必要があることをユーザーに伝える
3. 各ディレクトリ名の先頭10文字（`YYYY-MM-DD`）を開催日として解釈する
4. 今日以降の開催日を持つディレクトリのうち、最も開催日が近いものを書き込み先として自動選択する
5. 該当ディレクトリが1つしかない場合はそれを使う。判断に迷うケース（今日以降の開催日を持つディレクトリが複数あり優先度が読み取れない等）はユーザーに確認する

## Step 3: results.csv / splits.csv に追記する

選択した大会ディレクトリの `results.csv` にサマリー1行を追記する。スプリットデータが取得できていれば、同ディレクトリの `splits.csv` にも各kmを1行ずつ追記する。ヘッダー行はすでに存在するので、値の行だけを追加する。同じ `date` と `start_time` の組がすでに `results.csv` にある場合は、追記せずにユーザーに上書きか取りやめかを確認する。同じ日でも `start_time` が異なれば別の走行として追記する。

## Step 4: plan.mdと照合する

`plan.md` は曜日単位のメニューを持たない。進捗の基準は大会ごとに次のどちらかの形をとるので、まず `plan.md` を読んでどちらの形かを確認する。

**A. 週あたりの目安レンジがある場合**（「期分けと週の目安」の表に週の回数・週間距離がある）

照合は日単位ではなく週単位の積み上げで行う。

1. 抽出した `date` がどの期分けに属するかを期間の表から特定する
2. `results.csv` から、`date` を含む週（**起点は月曜**）の記録をすべて集計し、その週の走行回数と累計距離を求める。今回追記した行も集計に含める
3. 集計値を、特定した期の「週の回数」「週間距離」の目安レンジと突き合わせる
4. ロング走の距離目安・その期で重視する練習種別と、今回のペース・距離を照らし合わせる
5. 期の途中で目安レンジ内に収まっているかだけでなく、期の中で漸増できているかを見る

**B. 期ごとの到達目標と「走れるときの判断ルール」がある場合**

週単位の集計・目安との突き合わせは行わない。

1. 抽出した `date` がどの期分けに属するかを期間の表から特定する
2. その期の到達目標（歩かずに走り通すロング走の距離など）に対して、今回を含めた現時点の到達状況を求める。「歩かずに走り通した最長距離」はスプリットのペースから歩きを含む区間を除いて判断する
3. 判断ルールに照らして今回の内容が適切だったかを見る。直近の練習（前回からの間隔、直近7日のロング走・ポイント練習の有無）、1回で伸ばす距離の上限、直近7日間の回数・距離の上限、間が空いたあとの再開ルールを確認する

照合結果を書くときの制約（A・B共通）:

- 目安や到達目標を下回っていても「未達」という評価語は使わない。「レンジ下限に対して-5km」「到達目標14kmに対して現時点の最長11km」のように差分を事実として記録するにとどめる
- 走った曜日は判定材料にしない。休養日・練習日という区分は `plan.md` に存在しない

## Step 5: evaluations.mdに追記する

同じ大会ディレクトリの `evaluations.md` に、`## YYYY-MM-DD（曜日）` の見出しで新しいエントリを追記する（既存エントリの上書きはしない）。同じ日に2回目以降の走行を追記する場合は、見出しに開始時刻を添えて区別する（`## YYYY-MM-DD（曜日）HH:MM開始`）。

エントリの構成は、その大会ディレクトリの `evaluations.md` 冒頭にあるテンプレートに準拠する（`templates/evaluations.md` ではなく、大会ごとに調整された冒頭のテンプレートを正とする）。以下4観点すべてに具体的な内容を書く。空欄のまま残さない。

- **計画照合**: 該当する期分けと、Step 4の照合結果（Aなら週の目安レンジ・その週の走行回数・累計距離・差分、Bなら期の到達目標・現時点の到達状況・判断ルールとの照合）。差分は評価語ではなく事実として書く
- **目標に対する進捗**: `plan.md` に書かれた目標タイムに対して、今回のペース・心拍がどう位置づけられるか
- **体調・回復度・怪我リスク**: 心拍の上昇傾向、ペースの乱れ、直近の記録との比較から気になる点があれば指摘する。特に問題がなければその旨を書く
- **次回メニューの提案**: 今回の内容と、その期で重視する練習種別・残りの週の目安（Bの場合は判断ルール）を踏まえた具体的な提案。曜日は指定せず「次に走るとき」の内容として書く。Bの場合は、次に走れる時間がどれくらいとれるかで内容が変わるので、とれる時間ごとの内容を示す

### 定型の扱い（エントリには書かない）

次の事象は毎回同じ扱いとし、エントリでは触れない。通常と異なる出方をしたとき（扱いを変えるべき理由があるとき）だけ記載する。

- 走り出し直後（1〜2km目）の心拍が、前後の区間やペースに対して低い値になるのは、心拍が運動強度に追いつく前の立ち上がり遅れ・計測ずれとみなし、評価対象にしない。値は表示どおり記録する
- 最後の端数区間（終了操作前の短い区間）のペース・前km差は評価対象にしない
- 各kmの `elevation_change_m` の合計と、サマリーの上り・下りの差し引きが一致しないのは、各kmの値が区間の始点と終点の差で細かな起伏を含まないためであり、評価には影響しない
- 平均テンポ（ケイデンス）がこれまでの通常の範囲内であれば触れない

## Step 6: 変更をコミットしてpushする

Step 3〜5で変更した `results.csv` / `splits.csv` / `evaluations.md` をコミットし、`main` にpushする。コミットメッセージはConventional Commits形式（`feat: ...`）で、対象日付と内容が分かる一文とする。ユーザーから明示的な停止指示がある場合を除き、都度の承認を待たずにpushまで完了させる。

コミット・pushは必ず `main` ブランチに対して行う。セッション起動時に別の作業ブランチが指定されていても `main` を使う（`CLAUDE.md` の「ブランチ運用」を参照）。

## 参照ファイル

- `templates/evaluations.md`: 評価エントリのテンプレート
